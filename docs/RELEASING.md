# Сборка и релиз

## Один раз после создания репозитория GitHub

1. Загрузите содержимое именно этого каталога, а не родительскую исследовательскую папку.
2. Разрешите GitHub Actions. Workflow использует стандартный Ubuntu runner.
3. Создайте постоянный ключ подписи и сохраните резервную копию вне Git.
4. В Settings → Secrets and variables → Actions добавьте четыре repository secrets:

| Secret | Значение |
| --- | --- |
| `ANDROID_KEYSTORE_BASE64` | JKS-файл, закодированный base64 без переводов строк |
| `ANDROID_KEYSTORE_PASSWORD` | Пароль хранилища |
| `ANDROID_KEY_ALIAS` | Alias ключа |
| `ANDROID_KEY_PASSWORD` | Пароль ключа |

Пример создания ключа (путь за пределами репозитория; пароли вводятся интерактивно):

```sh
keytool -genkeypair -keystore /your/private/path/journal-release.jks -alias journal -keyalg RSA -keysize 3072 -validity 10000
```

Для PKCS12 Java может требовать одинаковые пароли хранилища и ключа. Для явного
формата JKS добавьте `-storetype JKS`. Значения паролей не передавайте в аргументах команд.
Получить base64 без вывода секрета в терминал можно в отдельный временный файл:

```sh
python3 -c 'import base64,pathlib; pathlib.Path("/your/private/path/key-base64.txt").write_text(base64.b64encode(pathlib.Path("/your/private/path/journal-release.jks").read_bytes()).decode())'
```

Содержимое этого файла вставьте в secret, затем удалите временный текстовый файл.
Сам ключ и его пароли обязательно сохраните: обновления должны иметь ту же подпись.
Никогда не публикуйте ключ в репозитории, Release или issue.

Ранние локальные APK подписаны debug-ключом. Новый release-ключ не позволит
установить обновление поверх них: сначала экспортируйте JSON, удалите старую
версию, установите релиз и импортируйте архив. Это одноразовый переход; далее
не меняйте release-ключ. Не выполняйте удаление приложения без экспорта данных.

## Когда вы решили выпустить новую версию

В обычной разработке версии не меняются. Только по решению владельца:

```sh
node scripts/version.mjs 0.3.0
```

Это пример будущей версии, не команда для обязательного немедленного запуска.
Скрипт обновит package.json, lockfile и versionName и увеличит versionCode.
Обновите `docs/release-notes.md`, проверьте изменения, затем закоммитьте их.
Отправьте соответствующий тег:

```sh
git push origin main
git tag -a v0.3.0 -m 'Prepare 0.3.0'
git push origin v0.3.0
```

Workflow `Release APK`:
- проверяет точное совпадение тега и файлов версий, увеличение versionCode относительно других релизных тегов;
- устанавливает зависимости по lockfile, запускает тесты;
- собирает общие assets, выполняет assembleRelease и lintRelease;
- подписывает APK постоянным ключом, проверяет подпись и zip alignment;
- прикладывает APK и SHA-256 к черновику релиза.

Установите APK из черновика и проверьте на реальном приборе. Затем вручную
опубликуйте Release. Простой push изменений версии без тега APK не выпускает.
Если сборка упала, исправьте причину; после настройки недостающих secrets можно
повторно запустить job через Re-run jobs. Уже опубликованный релиз workflow не перезаписывает.
Сохранение черновика через веб-форму само по себе сборку не запускает: триггер — push тега.

GitHub Actions не проверяет физическое BLE-соединение. Перед публикацией проверьте
сопряжение, повторное подключение, историю, завершение измерения и отсутствие ERR.
